# RC2 保存処理の改善・計画A（公開前の複製）

基点はmain `348c9f5dad5448147fa3a2a4864e4e0a29f353bf`。`rc2/index.html`を別パスへ複製し、在庫・取引8操作と台帳2操作の保存経路を変更した。`rc2/`本体、Worker、D1、Secretsは変更しない。Draft PRの準備までで、マージとGitHub Pagesへの公開は別承認。将来公開する場合も、このパスでダミーだけを使って確認する。実データのJSONを復元しない。noindexはアクセス制御ではない。

## 保存先と互換性

複製がアクセスするlocalStorageは次の3キーのみ。正式版キーは読み書きしない。

- `coupon_sales_release_rc2_storagetest`
- `coupon_sales_release_rc2_registry_v1_storagetest`
- `coupon_sales_release_rc2_backup_evidence_v1_storagetest`

ロック名は各キーに`:write`を付けたもの。キーごとに異なる。保存JSONの形、`version:3`、台帳schema `coupon-buyer-ledger-rc2-v1`、在庫バックアップschema `coupon-sales-release-rc2-v1`は維持する。`rev`、`datasetId`、`purchaseId`、`historyExt`、guardキーは追加しない。既存の未知項目を落とすための再構築も行わない。

`strictCheck`本体は改行を正規化した比較で基点と一致する。更新関数への`strictCheck`追加はしない。従来からある登録・起動・復元等の呼び出しは維持する。台帳の`validateBuyerLedger`も従来どおり保存前に行う。

`createStoragePlanA`は画面が読んだ元の保存文字列をメモリに保持する。保存は、ロック取得→最新文字列を取得→元の文字列と比較→最新JSONへ操作を適用→保存→読戻し照合の順。更新コールバックに非同期関数を渡すことは拒否する。確認ダイアログ、ファイル読込、通信はロック外。確認前・ファイル読込前の文字列を、待機後にも比較する。

文字列が違えば、その操作は書き込まず「変更あり」を表示して保存操作を停止する。画面上の再読込ボタンを押し、最新を読み直してから再操作する。未保存のフォーム入力は再読込で失われる。自動的な再実行・自動統合はしない。`storage`と`pageshow`は変更検知の補助で、排他の保証には使わない。同じ文字列に戻るABA変更は、この方式では検知できない。

Web Locks非対応なら、業務データの保存とコピーを拒否する。主要な保存ボタンを無効にして閲覧専用と案内する。保存領域の異常時も従来の停止を維持する。

業務データの保存後、必要なら補助情報を別ロックで保存する。複数キーの原子性はない。業務データ失敗と補助情報だけの失敗は別表示。補助情報に失敗しても業務データは巻き戻さず、補助情報の確認日時をメモリ上だけ先に成功へ変えない。補助情報の競合も、古い全体を書き戻さず警告する。

## コピーの同期経路と制限

コピーだけはWeb Locksを使わない。クリック処理内で、最新文字列の比較→最新JSONへのコピー準備適用→同期保存→保存後の読戻し照合→`clipboard.writeText`呼び出しを行う。`writeText`を呼ぶまでに`await`を入れない。`writeText`の返したPromiseを待つ箇所は従来どおり残す。

保存に失敗した場合、または直後の照合に失敗した場合はクリップボードへ渡さない。保存後の照合失敗では既に書き込まれた可能性があるため「保存済みか未確定」と警告し、勝手に巻き戻さない。

**このコピー経路と、別タブのコピー／ロック付き更新との競合は保証しない。** localStorageにはこの比較と書き込みをまとめるCASがなく、Web Locksはロックを使わない経路を止めない。保存後照合でも、その後に起きる上書きや、競合による変更消失をすべて検出できない。正式版への全面的な排他対策が完了したとは扱わない。

クリップボードだけ失敗した場合はコピー準備済み状態を保持し、現行どおり文面確認・手動コピーを案内する。再コピーで固定文面・`copyIntentAt`は変更しない。

## 中継と範囲外

中継の接続先・認証・リクエスト形式は基点と同じ。A/B修正で、閲覧専用・変更検知後の取得と再通知の開始は拒否する。既に送信済みのリクエストを巻き戻すものではない。RC2の中継入力は**受信キー（RECEIVER_KEY）**であり、送信キーではない。実機検証では入力しない。通常の手動ダミー登録だけでは、中継からステージされた項目がないため通知しない。`recordSaved`は在庫の保存成功後だけ呼ぶ。

## A/B追加修正：共有とボタンの停止維持

在庫と台帳の共有は、クリック処理内でファイルを作り、最初の`await`より前に`navigator.share()`を呼ぶ。共有Promiseが成功した後にだけ`markBackupCreated`を実行する。補助情報のロック待ちは共有を呼ぶ前に置かない。通常ダウンロードも開始操作を先に行う。

共有がキャンセル・拒否・同期例外で終わった場合は、この試行の`createdAt`・`pending`・`confirmedAt`を更新しない。過去の確認日時や過去の未確認記録も消去しない。共有成功は保存先のファイル存在を証明しないため、`pending=true`・保存未確認のまま。利用者がファイルを確認して「保存済みを確認」を押した場合だけ`confirmedAt`を更新する。ダウンロードも開始しただけでは保存確認済みにしない。

共有成功後に補助情報の保存が失敗しても、業務データや共有を巻き戻さない。専用の警告を残し、メモリ上だけ確認日時を成功にしない。Safariの共有メニューで実ファイルが保存されることは、公開後の実機確認として残す。

ボタンの再有効化は`storageWritesAllowed()`でWeb Locks対応と再読込待ちを再確認する。登録確認チェック、中継キー入力・消去・取得終了、補助情報の再描画でも停止を維持する。再通知ボタンも停止し、古い取得・通知コールバックを直接呼んでも新しい通信を開始しない。

購入履歴の同期受付は未実装のまま。台帳・履歴API、顧客の非表示・復帰、ID移行、データ移行、Worker/D1/Secretsの変更は含まない。正式版や旧タブとの同じキーでの共存試験でもない。
